# PLAN — explain-it-v2-voice (Local Kokoro TTS)

## Technical Context

| Field | Value |
|---|---|
| **Language/Version** | Python 3.14.4 (`C:\Python314`), PowerShell 5.1 |
| **Primary Dependencies** | `kokoro>=0.9.4`, `soundfile`, `torch` (CUDA wheel, auto-selected on Windows), `pynput`; system binary `espeak-ng` at `C:\Program Files\eSpeak NG\espeak-ng.exe` |
| **Storage** | Temp WAV files (required — `winsound.SND_LOOP` is incompatible with `SND_MEMORY`, so audio must be played from a file path) |
| **Testing** | Manual smoke test + end-to-end loop test; no test framework |
| **Target Platform** | Windows (win32); CUDA via RTX 3060 (12GB VRAM), 32GB DDR4, i7-11700F. CPU is fallback only. |
| **Performance Goals** | <5s first-response-to-audio on GPU (well under the ~2-5s CPU ceiling); <500ms mute via `Ctrl+Alt+M`; zero model reload after first call; <2GB VRAM (Kokoro footprint) |
| **Constraints** | Windows-only (`winsound` stdlib); local-only TTS (no cloud); must not corrupt the user's 2028-char PATH; preserve `explain-it-v2` pedagogy verbatim; original skill read-only; whole-response loop granularity; stop on ANY new message |
| **Scale/Scope** | 2 new scripts (`tts_server.py`, `speak.ps1`) + 1 cloned-and-edited `SKILL.md` + PATH fix + dep install; ~6 files touched total |

## Strategy

Layer ordering: **environment → verify engine → build daemon → build wrapper → wire skill → verify end-to-end.**

The daemon (`tts_server.py`) is the core — it holds the model in memory, generates WAV on demand, and controls infinite-loop playback via `winsound`. The wrapper (`speak.ps1`) is the thin agent-facing surface with lazy auto-start. The SKILL.md edit is the integration point where the cloned skill gains two audio instructions. GPU (CUDA) is the primary inference device (`device='cuda'`); CPU is the fallback if CUDA init fails.

The phases build bottom-up: get the environment ready, prove the engine works (smoke test), then layer the daemon, wrapper, and skill integration on top. Phases 2-4 are parallelizable (clone, daemon, wrapper are independent until Phase 5 wires them together).

## Phase 3 — Write `tts_server.py` `[P]`

- [ ] Create `.agents/skills/explain-it-v2-voice/scripts/tts_server.py`
- [ ] Load `KPipeline(lang_code='a', device='cuda')` ONCE at startup (wrap in try/except for CUDA → CPU fallback)
- [ ] HTTP server on `127.0.0.1:8765` using stdlib `http.server` (no web framework)
- [ ] Audio playback via `winsound`:
  - `/loop`: generate WAV → write to temp file → `winsound.PlaySound(path, SND_FILENAME | SND_LOOP | SND_ASYNC)` → return when audio starts
  - `/stop`: `winsound.PlaySound(None, SND_PURGE)` → instant silence
  - `/replace`: atomic swap (stop + generate + loop new)
  - `GET /status`: return `idle` or `playing`
- [ ] Global hotkey listener via `pynput.keyboard.GlobalHotKeys({'<ctrl>+<alt>+m': stop_fn}).start()` (non-blocking daemon thread, NOT `.join()`)
- [ ] Default voice config: `voice='af_heart'` (one-line config near top for easy change)
- [ ] Clean up temp WAV files after playback stops

**Exit gate:** Server starts, `GET /status` returns `idle`, `POST /loop` with text produces looping audio, `POST /stop` silences it. Can run in parallel with Phases 2 & 4.

### Risk / Rollback

- **CUDA init fails at smoke test (Phase 1):** fall back to `device='cpu'`. Latency rises to ~2-5s per response block. No daemon or wrapper change needed — just the `device=` argument. Documented in `tts_server.py` with a try/except.
- **`set_data_path` AttributeError fires (Phase 1):** pin `phonemizer<3.4` (or apply the one-line patch from issue #206: `EspeakWrapper.data_path = espeakng_loader.get_data_path()`). Retry the smoke test.
- **`Ctrl+Alt+M` conflicts with a running app (Phase 6):** change the hotkey string in `tts_server.py` (one-line config in the `GlobalHotKeys` dict). No other changes.
- **PATH fix doesn't propagate:** ensure a NEW terminal is opened (Phase 0 requirement). If still failing, use the Environment Variables GUI as a manual fallback.
- **Daemon won't start or crashes:** check `tts_server.py` logs (stdout/stderr in the detached process); common causes are missing deps (Phase 0 exit gate should have caught this) or port 8765 in use (change `PORT` constant in `tts_server.py`).

## What we are explicitly NOT doing

- Cloud TTS (Edge TTS, Google, ElevenLabs, etc.)
- Non-Windows porting (no macOS/Linux audio path; `winsound` is Windows-stdlib)
- Per-section audio looping (the whole response is one loop block)
- Altering `explain-it-v2`'s pedagogy in any way (audio is additive only)
- Auto-starting the daemon via opencode config hooks (`speak.ps1` lazy-starts instead)
- Voice cloning or custom voices
- Multi-language support (English only for v1; `lang_code='a'`)
- Real-time streaming audio (generation is batch-then-loop, not stream-as-you-go)
- `kokoro-onnx` as a planned phase (escape hatch only — noted in REFERENCES)
