## (b) Seed note (verbatim)

> "Subagent Review
> When creating something, stop allowing agents to review their own products. Always instruct agents to spawn review subagents on their work. (say 'spawn a read-only reviewer in a separate context; do not trust your own summary')"

## (c) Questions answered in order

### Q1. Concrete review-subagent workflows for code (†)

Eight distinct patterns found; the five with evidence ≥T2 are detailed in section (d). In brief: (1) **multi-model parallel review with cross-reference** (Nolan Lawson); (2) **autonomous per-commit inline PR reviewer** (The Daily Agent); (3) **writer/reviewer split, read-only diff reviewer** (Bernardo Secades); (4) **evidence-required agentic review loop** (Alexandre Castro/Archbot); (5) **five-agent pipeline with confidence filter** (Claude Code Review, independently tested by LogRocket); (6) **advisory-first then blocking PR review with skill-file rules** (Indpro); (7) **triage-first-pass AI review, human final approval** (daily.dev guidance); (8) **implementer→reviewer→fixer loop with softened fixer instructions** (Imbue, measured). Candidates below T2: multi-persona adversarial review with synthesizer (Graham Wheeler comment on Lawson's post, T3), reviewer-debate synthesis (Open Code Review, HN Show HN, T3), adamsreview multi-stage plugin (HN Show HN, T3, self-disclosed), Alibaba open-code-review file-bundling (T4, vendor).

### Q2. Triggers and reviewer context inputs

**Triggers reported:** PR opened (Indpro; LogRocket GitHub Action on every push; Castro; daily.dev), push to an open PR (The Daily Agent cron+event; LogRocket), branch marked done / before push or merge (Secades; Lawson; hidayetcanozcan pre-merge pipeline; Claude Code /ultrareview "before you merge"), on demand (Lawson's skill; HN commenter's `/meta-review` skill), and inside the agentic loop rather than only at PR stage (Imbue recommendation; HN commenter: "spin subagents, review… triage the review in another subagent, fix what's applicable, push back on what's not… in a loop. This is before you even open a PR").

**Context inputs reported:** the full diff (all sources; Secades makes the reviewer run `git diff main...HEAD` itself rather than accept a summary); acceptance criteria/spec (Secades); surrounding repo files (all; Castro's reviewer fetches files itself via tools); repo rules files — CLAUDE.md, REVIEW.md scope files, SKILL.md guardrails (LogRocket; Indpro); a bug-definition checklist (Lawson's skill: KISS/DRY, accessible HTML/JSX, SQL indexes); git blame/history and past PR comments (LogRocket agents 3–4; Qodo "PR history as a first-class signal"); test output rarely — Secades notes review is "static analysis by default" unless you allow `make test`. No source reported a reviewer receiving test output as standard input.

### Q3. Evidence that review subagents caught issues the author missed (†)

- **T2 — The Daily Agent (dev.to, 2026-04-26):** 43 review rounds on 3 PRs; 27 issues (8 RED, 11 YELLOW, 8 GREEN); 7/8 RED confirmed by human reviewers, 1 false positive; 9/11 YELLOW led to code changes; 2 misses reached staging. Specific catches: TOCTOU race in invite acceptance (duplicate membership), detached SQLAlchemy ORM object, missing `pointerEvents:'auto'` that "would have been a production incident within 48 hours," TOFU cache migration hazard that would have broken connections for 50+ team members. The author's own framing: the agent caught things "human reviewers had been looking at… and missed entirely."
- **T2 — Indpro (Tom Bergström, CTO, 2026-05-21):** week 1: 23 findings across 31 PRs vs 4 human findings — all 4 already flagged by the agent; 3 criticals fixed pre-merge (unhandled Promise rejection in payment handler, missing null check in subscription cancellation, workspace race condition); auth-bypass risk via request-body manipulation flagged because the agent "checks every route against the authorization pattern… regardless of PR size." Vendor-flag: Indpro sells this service; treat numbers as self-disclosed.
- **T2 — LogRocket (Ikeh Akinyemi, 2026-04-07):** independent test of Claude Code Review on a tRPC codebase: caught an auth bypass (removed session guard, confidence 100), a cross-file regression from a one-line field rename (stale reference in a file outside the diff), and a missing Zod validation. "None of these stand out on a skim."
- **T2 — Secades (claudecodesessions.com, 2026-07-07):** the writer session had "reviewed" the retry path minutes earlier and waved it through; the fresh-context reviewer found the duplicated event on retry. "Same model, same diff. The only thing that changed is that the reviewer's window doesn't contain the paragraph where the writer convinced itself the retry was safe."
- **T2 — Lawson (nolanlawson.com, 2026-05-25, HN 695 pts):** multi-model review "always finds tons of bugs in a PR, and the false positive rate is near zero"; commenters corroborate (Ollie: agent flagged an RLS policy gap "I would have shipped"; HN commenter: `/meta-review` "always finds little things claude & I missed").
- **T1 — Imbue (2026-04-29):** on SWE-bench Pro, reviewer+fixer lifted one task from 22/23 to 23/23 consistently; on 15 fully-resolved tasks the reviewer found real issues in 8 (6 test-coverage, 2 logic). Mean score across 175 tasks did not move significantly — the honest counterweight.
- **T1 — Martian Code Review Bench (2026-02):** independent benchmark (50 human-golden PRs offline; continuous online set): best tool (CodeRabbit) F1 ≈51.2%, precision ≈49.2%, recall ≈53.5% — i.e., even the best reviewer misses roughly half of real issues and ~half its comments are noise. This is tool-level, not subagent-level, but it calibrates every anecdote above.

### Q4. Failure modes reported

- **False positives:** Daily Agent 2/27; Indpro 3/23 (13%, all from one un-encoded exception to a skill rule); daily.dev cites "50% to 80% of AI comments can be noise or false positives" and Kunal Ganglani estimates 15–30% low-value comments; Castro's Archbot produced a confidently-wrong "blocker" that cost a senior engineer 20 minutes to disprove (missing guard clause two files away — a context problem, not a prompt problem).
- **Rubber-stamping / false confidence:** Tian Pan (2026-04-23) describes "rubber-stamp collapse" — reviewers approving AI-authored PRs they haven't deeply read; Kunal: "AI code review doesn't fail by missing bugs — it fails by making you stop looking for them" (green-checkmark complacency); daily.dev: "AI approval ≠ human approval" must be explicit policy.
- **Reviewer adopting the author's assumptions:** Secades — the dispatch prompt can leak framing ("branch name + criteria only" is a discipline, not a mechanism); Lawson — the main agent must not do its own research until all three reviewers return, "otherwise there's a tendency to be influenced by the first result"; Kunal — "recursive blind spot" when the same model family writes and reviews.
- **Review noise:** LogRocket — pre-existing bugs surfaced on unrelated PRs (a 1-line PR producing comments against 5 other files); Lawson — "you'll be bored senseless if you try to tackle them all."
- **Reviewer editing code against the author's intent:** Imbue (T1) — the fixer agent "overreached," rewriting rounding logic while adding requested tests, breaking a test it then misattributed; with full-detail review comments a Sonnet fixer restructured 8 files (113 lines) and dropped a task from 16/17 to 8/17 (Δ=−8). Summary-only comments and "softer" fixer instructions eliminated catastrophic regressions.

### Q5. Authority scoping

- **Read-only** is the most-recommended default: Secades (no Edit/Write tools — "a reviewer that can patch starts patching, and you lose the boundary that made its judgment trustworthy"); qatechtools QA guide ("start with read-only or limited tools"); AgentCheck (five read-only reviewers). Findings cross back as text; the writer applies them.
- **Propose-diff / advisory:** Zof's governance principle "agents propose, humans authorize"; daily.dev — advisory by default, blocking only for deterministic checks (secrets, missing files, lint); Indpro — advisory mode for 3 weeks, then blocking for critical/high only, because "teams that flip to blocking mode immediately tend to get pushback."
- **Fix-inline / auto-fix:** Imbue's measured warning — auto-fixing works but the fixer's quality dominates outcomes; use softened instructions ("address when confident, skip otherwise") and let humans handle skipped issues. adamsreview's `fix` command re-reviews fixes with a stronger model and reverts regressions before committing (T3, self-disclosed).
- **Recommendation consensus:** read-only review + human-applied fixes for beginners; if auto-fix, soft instructions + validation + human authorization.

### Q6. Token/cost/latency overhead and mitigations

- **Reported costs:** $0.50/review round, ~$21/week for 43 rounds (Daily Agent); $15–25/review (Anthropic Code Review pricing, per LogRocket); $5–20/run for /ultrareview (shareuhack); ~30k tokens burned by the reviewer vs ~600 returned to the main session (Secades); ~$7 to run 50 PRs through one reviewer (HN commenter, Coducky); custom pipeline $5–40/user/month API + 4–8 h/month maintenance (Kunal); CodeRabbit $24–48/user/month, Copilot ~$19, Cursor ~$20 (Kunal).
- **Mitigations reported:** diff-only review (Secades); single-pass with severity ladder and "don't pad" instruction (Secades); checklist-scoped review via REVIEW.md/skill files (LogRocket, Indpro, Lawson); confidence threshold filtering (LogRocket's 80-point cutoff; scoring subagents that try to disprove findings); finding caps (daily.dev: 5–8 per PR); batching/parallelism (Lawson's 3 models in parallel; Alibaba's file bundling into isolated-context subagents; adamsreview's JSON state to clear context between stages); aggressive context shrinking in the loop (Castro); "only fix what both point out" (note.com summary of Lawson).

### Q7. Which findings practitioners act on vs dismiss (†)

- **Severity ladders are the universal triage device:** RED/YELLOW/GREEN (Daily Agent — "If everything is a warning, nothing is"); blocker/should-fix/nit (Secades, Castro); critical/high/medium/low (Lawson, Indpro).
- **Evidence requirements:** Castro — every blocker/should-fix must cite path+line; "if you cannot cite evidence, downgrade to nice-to-have or omit"; structured submission schema enforces it. LogRocket — confidence ≥80 after an adversarial scoring pass; note the tradeoff: a real bug scored 75 was filtered ("noise suppression or information suppression depends on your team's risk tolerance").
- **Thresholds and metrics:** daily.dev — dismissal rate <20% healthy, >30% warning; cap 5–8 findings/PR; Indpro — <15% FP workable in advisory, <5% target for blocking.
- **Owner judgment rules:** Lawson — fix all criticals/highs (with guidance), repeat until none; skip mediums where "the juice isn't worth the squeeze"; abandon the PR if too many criticals ("the whole approach is misguided"). Daily.dev — human owns the merge decision; require a one-line reason for every accepted/dismissed finding. Ashton Antony (Lawson comment): triage still requires domain knowledge — "a junior who can't distinguish a real race condition from a theoretical one is still going to get overwhelmed."

### Q8. Minimum viable setup and barriers (†)

**MVP (synthesized from Secades + Lawson + Castro):** one read-only subagent defined in a repo-committed markdown file; prompt = "You did not write this code and have no stake in it. Run `git diff main...HEAD` yourself; read surrounding code; report only behavior/correctness/security findings with severity (blocker/should-fix/nit) and file:line; if nothing real, say 'approved' and list what you checked — never pad." Permissions: read/grep/glob/bash, no Edit/Write. Trigger: branch done, before push. Two rounds max, then a human. This is copy-pasteable from Secades' post.

**Barriers reported:** (1) **Config/prompt quality** — Lawson: "you'll probably want to tweak it for your particular codebase"; Castro: "iterate on tools, not prompts"; Indpro: skill-file exceptions must encode intentional deviations or FPs recur. (2) **Cost** — multi-model setups are expensive (Lawson: "I'm happy to wait 20 minutes for a better review"; Wheeler: "burns a lot of tokens"). (3) **Trust** — false positives erode trust fastest; advisory-first deployment and dismissal-rate tracking are the reported fixes (Indpro, daily.dev). (4) **Triage skill** — the reviewer's output is only as good as the human's ability to judge it (Ashton Antony). (5) **Noise volume** — Lawson: findings volume can be overwhelming ("bored senseless").

## (d) Workflow candidates (trigger / procedure / evidence)

**W1 — Multi-model parallel review with cross-reference.** Trigger: PR ready, before merge, on demand. Procedure: spawn 3 independent reviewers (e.g., Claude sub-agent, Codex, Cursor Bugbot) on the same PR; each ranks bugs critical/high/medium/low; main agent waits for all three, then does its own verification to kill false positives, writes one report; fix criticals/highs, repeat; skip mediums; abandon if too many criticals. Evidence: T2 — Lawson (2026-05-25): "always finds tons of bugs… false positive rate near zero"; HN 695 pts; corroborated by commenters (meta-review skill; RLS gap catch). Tradeoffs: 3× cost/latency; requires cross-model access. Adoptability: medium — needs multiple tools; a 2-model variant is the reported minimum (note.com).

**W2 — Autonomous per-commit inline PR reviewer with severity ladder + persistent tracker.** Trigger: push to open PR (cron + event). Procedure: agent reads full diff each round, posts inline comments with RED/YELLOW/GREEN and comment IDs; per-PR tracker prevents re-flagging resolved issues. Evidence: T2 — Daily Agent (2026-04-26): 43 rounds, 27 issues, 7/8 RED confirmed, 9/11 YELLOW → changes, 2 misses, $0.50/round. Tradeoffs: needs hosting/CI; noise control depends on the tracker. Adoptability: medium — infrastructure, but the pattern (severity + IDs + tracker) transfers to any harness.

**W3 — Writer/reviewer split, read-only diff reviewer.** Trigger: branch done, before push. Procedure: repo-committed subagent definition; read-only tools; reviewer pulls `git diff main...HEAD` itself; severity ladder; explicit "approved" when clean; two rounds then human. Evidence: T2 — Secades (2026-07-07): caught the retry-path duplication the writer session had waved through; ~30k tokens per pass. Tradeoffs: static-analysis-only by default; same-model blind spots persist. Adoptability: high — one file, copy-pasteable, cheapest.

**W4 — Evidence-required agentic review loop.** Trigger: PR opened/updated. Procedure: reviewer gets tools (diff, search_code, get_file_content, base version) and loops until it submits a structured review; every blocker/should-fix must cite path+line; no evidence → downgrade/omit; iteration caps and context shrinking as guardrails. Evidence: T2 — Castro (2026-03-09): before = confidently-wrong blocker costing 20 min to disprove; after = "cites file:line or stays quiet." Tradeoffs: more engineering (tool contracts, loop); latency. Adoptability: low-medium for a beginner — this is the "build your own" tier.

**W5 — Five-agent pipeline with confidence filter.** Trigger: PR opened (CI on every push) or manual. Procedure: triage agent → summary+diff agents → 5 specialized agents in parallel (rules compliance, bug sweep, git blame, past-comment patterns, comment accuracy) → scoring subagents try to disprove each finding → only ≥80 confidence posted inline. Evidence: T2 — LogRocket (2026-04-07): caught auth bypass, cross-file rename regression, Zod violation; also filtered a real bug at 75. Tradeoffs: product-specific (Anthropic Code Review); $15–25/review. Adoptability: low for self-hosting, high as a managed service.

**W6 — Advisory-first, blocking-later skill-file review.** Trigger: PR opened; blocking for critical/high after calibration. Procedure: reviewer checks every change against repo skill files (auth patterns, validation rules); severity buckets; advisory 3 weeks, then blocking; encode intentional exceptions as annotations. Evidence: T2 (vendor-flagged) — Indpro (2026-05-21): 23 vs 4 findings, 13% FP week 1 → 0 in category after annotation fix; review cycles 2.1 → 1.4. Adoptability: medium — requires maintaining skill files.

**W7 — Triage-first-pass with human final approval.** Trigger: PR opened, before human review. Procedure: self-review → AI first pass → author fixes/dismisses with one-line notes → human review → human merge; cap 5–8 findings; track dismissal rate. Evidence: T2 procedural (daily.dev, 2026-07-20; cites Macroscope 2025: AI detects 42–48% of real bugs). Adoptability: high — process change, no new infra.

**W8 — Implementer→reviewer→fixer loop with softened fixer instructions.** Trigger: after implementation, before merge (and in-loop for small changes). Procedure: strong implementer, reviewer comments, weaker fixer with "address when confident, skip otherwise"; summary-only comments; humans handle skipped issues. Evidence: T1 — Imbue (2026-04-29): mean no significant change; overreach regressions eliminated by soft instructions (Δ=−8 → 0); consistent lift on one task. Adoptability: medium — the measured lesson (fixer quality + soft instructions) transfers to any auto-fix setup.

## (e) Failure modes and adoptability barriers

See Q4/Q8. Headline: the dominant failure mode is not missing bugs but **noise + false confidence** (T2×3, T1-adjacent benchmark); the dominant structural risk is **same-context/same-model review** (Secades, Lawson, Kunal); the dominant measured risk in auto-fix setups is **fixer overreach** (Imbue, T1). Barriers for a beginner: prompt/config tuning, cost of multi-model setups, trust erosion from FPs, and the triage skill the human must bring.

## (g) Headline

The three most adoptable patterns for a review-agent beginner: **(1) the read-only diff-reviewer subagent** (W3, T2 — one committed markdown file, no Edit/Write tools, reviewer pulls its own diff, blocker/should-fix/nit ladder, "approved" when clean; caught a bug the author session had explicitly waved through); **(2) triage-first-pass review with human final approval** (W7, T2 procedural — AI reviews first, author fixes/dismisses with one-line reasons, human owns merge; cheapest process change with the clearest anti-rubber-stamp rules); **(3) multi-model cross-referenced review** (W1, T2 — three independent reviewers, fix only what survives cross-checking; near-zero false positives reported, at 3× cost — start with two models). The measured caveat from Imbue (T1) and Martian (T1) applies to all three: reviewers catch real issues but miss roughly half of them, and auto-fixing review findings without soft instructions can make correct code worse — so keep the reviewer read-only and the human in the loop.
